การเรียกครั้งนี้เป็นแบบอัตโนมัติ ให้ทำตามข้อความนี้เท่านั้น
- ถ้า AGENTS.md หรือ CLAUDE.md ของโปรเจกต์สั่ง workflow อื่น (เช่น TASK.md, temp-context, 10 ขั้น, invoke-claude) ให้ข้ามส่วนนั้น ส่วนความรู้เกี่ยวกับโปรเจกต์ในไฟล์เหล่านั้นใช้ได้
- คุณมีสิทธิ์อ่านอย่างเดียว ห้ามพยายามแก้ไฟล์ ให้ส่ง spec กลับมาในคำตอบ แล้ว arbiter จะเขียนไฟล์เอง

## อ่านเองตามลำดับ
1. การ์ด {{KEY}} จาก Jira (`mcp__jira__jira_get_issue`) รวมถึง parent/epic และการ์ดที่ลิงก์ ถ้าเกี่ยวข้อง
2. ถ้ามีอยู่แล้ว: `{{CARD_DIR}}/intent.md`, `spec.md` (ร่างเดิม), `questions.md`, `answers.md`
   คำตอบใน `answers.md` คือการตัดสินใจของผู้ใช้ ต้องทำตาม
3. `.arbiter/CURRENT_STATE.md` ถ้ามี
4. Recon โค้ดที่เกี่ยวข้อง: โครงสร้าง, pattern ที่ใช้อยู่, เทสต์ที่มีอยู่, คำสั่ง build/test

ห้ามถามสิ่งที่หาเองได้จากโค้ดหรือการ์ด

## Spec (ไม่เกินประมาณ 40 บรรทัด)

```
# {{KEY}}: <ชื่องาน>
## Goal
1–3 บรรทัด
## Non-goals
## Acceptance Criteria
AC1..ACn ทดสอบได้ เขียนแบบ Given / When / Then
## Approach
3–6 bullet ระดับไฟล์/คลาส ตาม pattern ที่ repo ใช้อยู่
## Assumptions
## Risks
```

ปิดท้าย spec ด้วยบล็อกนี้เสมอ (arbiter อ่านด้วยโปรแกรม):

```arbiter
scope_allow:
  - path/or/glob/**
verify:
  - <คำสั่งทดสอบเฉพาะการ์ดนี้ ถ้ามี>
```

- `scope_allow`: แคบที่สุดที่งานนี้ทำได้ รวมไฟล์เทสต์ที่ต้องเพิ่มหรือแก้
- `verify`: ไม่บังคับ ใส่เฉพาะคำสั่งที่ตรวจงานนี้ได้ตรงจุด (เทสต์ชุดหลักของโปรเจกต์ arbiter รันให้อยู่แล้ว)

## Questions (0–5 ข้อ)
ถามเฉพาะเรื่องที่หาจากโค้ดไม่ได้: business rule, โจทย์ที่ตีความได้หลายแบบแล้วผลต่างกัน, ขอบเขต, การตัดสินใจที่ย้อนยาก (schema, API contract, ข้อมูลจริง)
- ทุกข้อต้องมีตัวเลือก และ `[default: ...]` ที่จะใช้ถ้าผู้ใช้ไม่ตอบ
- ถ้าการ์ดไม่มี acceptance criteria ชัดเจน ให้ถามหนึ่งข้อว่า "ถ้าตอน Gate 2 คุณจะตีงานนี้กลับ น่าจะเป็นเพราะอะไร"
- ไม่มีคำถามที่จำเป็นจริง ให้ตอบ NONE
