## ตรวจ
- AC แต่ละข้อมีโค้ดรองรับ และมีเทสต์ที่ตรวจพฤติกรรมจริง (ไม่ใช่เทสต์ที่ผ่านเสมอ หรือ mock จนไม่ได้ทดสอบอะไร)
- ความถูกต้อง: edge case, null, error handling, transaction, concurrency ที่เกี่ยวข้อง
- ทำเกินหรือขาดจาก spec และ Non-goals
- กระทบพฤติกรรมเดิม, config, หรือความปลอดภัย (secret, injection)

รายงานเฉพาะปัญหาที่ชี้ `ไฟล์:บรรทัด` ได้ ให้ระดับ BLOCKER / MAJOR / MINOR
VERDICT เป็น FAIL ถ้ามี BLOCKER หรือ MAJOR อย่างน้อย 1 ข้อ ไม่มีให้เป็น PASS
ข้อที่อ้างพฤติกรรมของเครื่องมือ (lint, framework, library) ที่คุณยืนยันจากเอกสารหรือโค้ดไม่ได้ ให้เขียนว่า "ยังไม่ยืนยัน" ในข้อนั้น
เขียน FINDINGS, UNTESTED และ LOOK_AT ให้คนอ่านเข้าใจโดยไม่ต้องเปิดโค้ด

VERDICT เป็น SPEC_ISSUE แทน FAIL เมื่อปัญหาอยู่ที่ spec เอง ไม่ใช่ที่งาน เช่น Approach ทำไม่ได้จริง, AC ขัดกันเอง,
หรือถ้าทำตาม spec ตรงตัวจะได้ผลผิด แก้ที่งานอย่างไรก็ไม่หาย ห้ามใช้ SPEC_ISSUE แทน FAIL ธรรมดา
ถ้าเป็น SPEC_ISSUE ให้เขียน SPEC_CHANGE: ข้อที่ต้องแก้ใน spec (AC/Approach/scope_allow/verify) และเหตุผล

## รูปแบบคำตอบ (บังคับ ห้ามมีข้อความอื่นนอก marker)

===VERDICT===
PASS, FAIL หรือ SPEC_ISSUE
===SPEC_CHANGE===
(เฉพาะ SPEC_ISSUE) ข้อเสนอแก้ spec ไม่มีให้เขียน "ไม่มี"
===FINDINGS===
- [MAJOR] path/File.java:42 ปัญหา → วิธีแก้
(ไม่มีปัญหา ให้เขียน "ไม่มี")
===UNTESTED===
สิ่งที่ยังไม่ได้ทดสอบ หรือทดสอบไม่ได้ในรอบนี้
===LOOK_AT===
1–3 จุดที่คนควรเปิดดูเองตอน Gate 2
===END===
