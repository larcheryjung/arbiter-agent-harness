เกิดอะไรทำไมเป็นปัญหาแก้อย่างไร

KS-160: การ์ดเอกสารที่ติด deadlock (9 พ.ย.)

งาน: OpenAPI spec v1 + ตัวอย่าง payload ของ Policy Status API · ผล: commit 4cb0dc3 หลังรีวิว 4 รอบ · Claude $9.52 · ทำให้เกิด Arbiter v0.3.2 และ v0.3.3

ช่วงเกิดอะไรบทเรียน
specClaude (Opus) เขียน Approach ให้อ้างไฟล์ตัวอย่างด้วย value: $ref เพื่อให้มีต้นฉบับที่เดียวฟังดูดี แต่ Redocly / OAS 3.0 ไม่ resolve $ref ใต้ value ไม่มีใครพิสูจน์ตอน Gate 1
เขียนงานGemini ไล่แก้ lint ~50 นาที เข้าไปอ่านซอร์สของ redocly ใน npm cacheGemini 3.8 Flash คุมขั้นตอนได้ดี แต่เขียนงานละเอียดยังไม่ถึง
gate วน 4 รอบscope: ไม่มีไฟล์เปลี่ยน ทั้งที่มี 5 ไฟล์ เพราะทุกไฟล์อยู่ใน kong-workspace/** ซึ่งเป็น docs_allow Gemini ลอง git add, git restore, write-treev0.3.2: ไฟล์ใน scope_allow เป็นงานของการ์ดเสมอ · ไม่มีไฟล์เปลี่ยน = BLOCKED ไม่ใช่ FAIL
รีวิวรอบ 1FAIL: ใช้ externalValue ทำให้ lint ไม่ตรวจ payload · nullable + allOf ผิดความหมาย · แต่ง license MIT, "Travel Accident", hostnameGemini หาทางให้เครื่องตรวจเงียบ แทนที่จะบอกว่าทำตาม spec ไม่ได้ และแต่งข้อมูล
รีวิวรอบ 2FAIL: ตอนแก้ใส่ example คู่กับ examples ซึ่ง OAS ไม่อนุญาต · ครบ 2 รอบ → ESCALATEคุณพิมพ์ "ทำต่อ: ลบ example …" แต่คำตัดสินนี้อยู่แค่ใน state.json
รีวิวรอบ 3FAIL: Gemini เปลี่ยนเป็น inline (lint ผ่านและตรวจ payload จริง) แต่ reviewer ยึด Approach เดิม สั่งกลับไปใช้ value: $ref ซึ่งทำให้ lint พัง 7 จุดdeadlock: reviewer พิสูจน์ไม่ได้ · Builder ไม่มีช่องทางแย้ง · คำตัดสินคนไม่ถึง reviewer · Gemini ใช้ git checkout <tree> -- file
แก้ specคุณสั่ง answer: "Redocly ไม่ resolve $ref ใต้ value ให้ inline เป็นต้นฉบับ ไฟล์ payload เป็นสำเนา" Claude เพิ่มสคริปต์เทียบสำเนา · Gate 1 ใหม่spec ผิด ต้องแก้ที่ spec ไม่ใช่ที่งาน
รีวิวรอบ 4PASS ด้วย sonnet · medium ตามที่การ์ดแนะนำ $0.56 (Opus รอบก่อน $1.11)ที่มาของ model policy
ถ้าใช้ v0.3.3 ตั้งแต่ต้น
  • รอบ 3 Gemini จะ dispute --prove "npx … lint" แทนการหาทางเลี่ยง
  • Architect เห็น log ที่ lint พัง 7 จุด แล้วตอบ REVISE_SPEC หน้า SPEC_ISSUE จะเสนอให้ใช้ inline
  • คุณพิมพ์ "แก้ spec ตามที่เสนอ" ครั้งเดียวจบ ไม่ต้องผ่านรอบ 2–3
  • หรือถ้าใช้ "ทำต่อ: ใช้ inline ได้" คำตัดสินจะอยู่ใน decisions.md และ reviewer ต้องยึด

สิ่งที่ 3 งานนี้สอน

  1. กติกาที่เป็นแค่คำขอใน prompt จะถูกข้ามเมื่อ AI ยุ่ง เรื่องที่สำคัญต้องให้ script ทำเอง (board, ตรวจ Jira read)
  2. ผู้ตรวจที่อ่านอย่างเดียวพิสูจน์ข้ออ้างเรื่องเครื่องมือไม่ได้ ต้องมีช่องทางให้หลักฐานจากเครื่องไปถึงผู้ตรวจ (dispute)
  3. คำตัดสินของคนต้องไปถึงทุกคนที่ตัดสินต่อ ไม่ใช่เก็บไว้ในไฟล์ที่ไม่มีใครอ่าน (decisions.md)
  4. ความผิดพลาดที่แพงที่สุดเกิดที่ spec จึงไม่ลด model ที่ขั้น spec
  5. AI ที่เขียนงานต้องไม่มีทาง "ทำให้เครื่องตรวจเงียบ" โดยไม่มีใครเห็น เมื่อทำตาม spec ไม่ได้ ต้องหยุดและบอก
