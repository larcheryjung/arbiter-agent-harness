อะไรบังคับจริง อะไรเป็นแค่กติกา

กติกาทุกข้อของ harness แบ่งได้ 2 แบบ: เครื่องบังคับ (AI ฝ่าไม่ได้ ต่อให้ลืมหรือตั้งใจ) กับ กติกาใน prompt (AI ควรทำตาม แต่ฝ่าได้) การรู้ว่าข้อไหนเป็นแบบไหน ช่วยให้รู้ว่าต้องเฝ้าดูตรงไหน

3 ชั้นของ harness

ชั้นคืออะไรตอนนี้มี
1. Safety floorโค้ดที่ใช้กับทุกงาน ไม่กิน context ของ AIgit pre-commit ✅ · jira-guard ✅ · pre-push ❌ · กันเขียน HBS DB / prod ❌
2. Trackท่าทำงานตามขนาดงาน (workflow ของ Gemini + template ของ Claude)/feature /spike ✅ · /poc /quick Ops ❌
3. Packความรู้เฉพาะเรื่อง โหลดเมื่อเกี่ยวข้องยังไม่มี (jira-ks, spring-boot, docker-deploy, windows-ps, pch-network)

เครื่องบังคับ

ที่ไหนบังคับอะไร
arbiter reviewไฟล์ที่เปลี่ยนต้องอยู่ใน scope · verify ต้อง exit 0 · คำสั่ง verify จาก spec ห้ามมี | & ; < > ` (กันการซ่อน exit code) · โค้ดห้ามเปลี่ยนระหว่างรัน verify · Claude ต้องตอบตาม marker ไม่งั้น ERROR · spec ต้องตรงกับที่อนุมัติ
arbiter specการ์ด KS ต้องมีหลักฐานจาก stream ว่า Claude เรียก jira_get_issue ของการ์ดนั้นสำเร็จ ไม่งั้นไม่รับ spec
arbiter commitevidence ผ่านทั้ง gate และ review · spec sha ตรง Gate 1 · ไม่มี drift · ไม่มีไฟล์นอก scope · สิ่งที่ stage ตรงกับที่รีวิวทุกไบต์ · การ์ดไม่ถูกพัก
git pre-commit (fail-closed)โค้ด commit ได้เฉพาะผ่าน arbiter commit ที่มี Gate 2 ของ tree นั้น · scope ของการ์ด ACTIVE · ความลับ (private key, AWS access key, Atlassian token, GitHub token) · ไฟล์ .env / คีย์ SSH · ห้าม commit config.json · เอกสารล้วนผ่านได้ · hook พังเอง = บล็อก
configarbiter ใช้ config.json ฉบับที่ commit แล้วเท่านั้น ถ้าไฟล์ในเครื่องต่างไป arbiter หยุด (กัน AI แอบขยาย docs_allow หรือลบ verify) · hook อ่าน docs_allow จาก HEAD
claude -pมีแค่ Read / Grep / Glob · ปฏิเสธ Edit / Write / Bash / PowerShell · Jira อ่านอย่างเดียว · การ์ด LOCAL ไม่มีเครื่องมือ Jira
JiraKS เท่านั้น 3 ชั้น: credential เห็นแค่ KS · mcp-atlassian --jira-projects-filter KS · hook ระดับผู้ใช้ ~/.claude/hooks/jira-guard.py · arbiter_board.py ส่งได้เฉพาะรหัส KS-n (เขียนไว้ในโค้ด ไม่ได้อ่านจาก config)
disputeคำสั่งพิสูจน์ห้ามมี shell meta · 1–3 คำสั่ง · ไม่เกิน 2 ครั้งต่อการ์ด

กติกาเคยถูกฝ่า
Gemini แสดงข้อความของ arbiter ตามตัวอักษรก่อนเสมอ ห้ามใช้สรุปแทน ห้ามตอบหรืออนุมัติแทนคุณKS-118 (แต่งเหตุผลเอง) · KS-160 (สรุป spec เองแทนการแสดง)
"สรุปจาก Builder" (v0.3.6) ต่อท้ายหน้าที่รอคุณตัดสิน: ข้อเท็จจริงมาจากข้อความข้างบนหรือที่ Builder ตรวจเอง ห้ามข้าม finding / "ยังไม่ได้ทดสอบ" ความเห็นต้องกำกับว่าเป็นความเห็นยังไม่มีข้อมูล · ข้อควรระวัง: Builder สรุปผลรีวิวงานของตัวเอง ที่ Gate 2 ให้ถือข้อความของ arbiter และ gate2.md เป็นตัวจริง
ห้าม git checkout / restore / reset / stash / cleanKS-118 (เกือบทับรายงาน) · KS-160 ใช้ git checkout <tree> -- file 2 ครั้ง
ห้ามหาทางเลี่ยงเครื่องตรวจ ให้ใช้ disputeKS-160 เปลี่ยนเป็น externalValue จน lint ไม่ตรวจ payload
ห้ามแต่งข้อมูลที่ไม่มีที่มา ใช้ TODO / placeholderKS-160 แต่ง license MIT, "Travel Accident", hostname ที่ดูเหมือนจริง
ห้ามอ่านซอร์สของ arbiter และห้ามแก้ .arbiter/KS-118 อ่าน arbiter.py หา env ที่ hook เชื่อ
ห้ามห่อคำสั่ง arbiter ด้วย python -cKS-160 ห่อแล้วข้อความไทยพัง ผลหาย
HBS Oracle อ่านอย่างเดียว (SELECT)ยังไม่เคยถูกฝ่า · ใช้ user readonly เป็นชั้นป้องกันหลัก
วิธีอ่านตารางนี้ ทุกครั้งที่กติกาใน prompt ถูกฝ่าซ้ำ ให้ถามว่า "ย้ายไปไว้ในเครื่องได้ไหม" (หลักแกนข้อ 7) เช่นเรื่อง board ที่ Gemini ลืม ถูกย้ายมาให้ arbiter ทำเองใน v0.3.2 ส่วน git checkout ยังย้ายไม่ได้ เพราะ git ไม่มี hook ที่ใช้บล็อกคำสั่งนี้

ช่องโหว่ที่รู้แล้ว

  • ไฟล์ใน .arbiter/ (approvals, evidence, state) agent ยังเขียนได้ การข้าม Gate 2 ต้องปลอมการอนุมัติของคน ซึ่งเห็นได้ใน transcript แต่ยังไม่ถูกบล็อก (แผน: ย้ายหลักฐานไป .git/arbiter/)
  • agent รัน approve หรือ --continue แทนคนได้ ตรวจย้อนหลังได้จาก transcript เท่านั้น
  • git commit --no-verify ข้าม hook ได้ ตั้งใจให้คนใช้สำหรับ config (แผน: CI ตรวจ trailer Arbiter-Tree)
  • ย้ายโฟลเดอร์ arbiter แล้ว hook หายเงียบ เพราะ core.hooksPath ชี้ path เต็ม ต้องรัน install ใหม่ทุกโปรเจกต์
  • ความลับใน transcript ใน SPIKE-1 Gemini เปิดไฟล์ .secret ทั้งไฟล์ และใส่รหัสผ่าน DB ลงในคำสั่งตรงๆ ซึ่งค้างอยู่ใน transcript ควรมีสคริปต์ต่อ DB ที่อ่านรหัสจาก env
  • Claude ใน claude -p อ่านไฟล์นอก repo ได้ (Read ไม่จำกัด path) ถ้าจะจำกัดจริงต้องใช้ permission rule แบบ deny
  • haiku ตัดสิน review ไม่สม่ำเสมอ ใช้ได้แค่ smoke test

ลองตอบ

ถ้า Gemini พยายาม git commit โค้ดเอง จะเกิดอะไร pre-commit hook บล็อก เพราะโค้ด commit ได้เฉพาะผ่าน arbiter commit ที่มี Gate 2 ของ tree นั้น เว้นแต่ใช้ --no-verify ซึ่งเห็นได้ใน transcript
Gemini แก้ config.json เพื่อเพิ่ม docs_allow ให้ตัวเอง จะได้ผลไหม ไม่ได้ arbiter ใช้ config ฉบับที่ commit แล้วเท่านั้น และจะหยุดทำงานทันทีที่เห็นว่าไฟล์ในเครื่องต่างไป hook ก็ไม่ให้ commit config.json
