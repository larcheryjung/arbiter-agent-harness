2. ส่ง "ตัวชี้" ไม่ส่ง "การตีความ"

นี่คือหลักที่ทำให้ Arbiter ต่างจาก harness เดิมมากที่สุด เวลา Gemini ต้องการให้ Claude ทำอะไร Gemini ส่งได้แค่ 2 อย่าง:

  • ตัวชี้ เช่นรหัสการ์ด KS-160 หรือ path ของไฟล์แนบ
  • คำพูดของคุณตามตัวอักษร ห้ามแก้ ห้ามเติม ห้ามสรุป

arbiter ใส่สองอย่างนี้ลงใน template ที่อยู่ในโฟลเดอร์ prompts/ แล้ว Claude ไปอ่านต้นทางเอง (การ์ดใน Jira, โค้ด, spec, diff)

แบบเดิม (AeroHarness)Builder เขียน architect-prompt.txt: "ช่วยรีวิวหน่อย ผมแก้ปัญหา X ด้วยวิธี Y ซึ่งถูกต้องแล้ว" ผู้ตรวจเห็นแค่สิ่งที่ Builder เลือกให้เห็น
แบบ Arbiterarbiter review KS-160 → Claude อ่าน spec.md ที่คุณอนุมัติ + diff + ผลตรวจจากเครื่อง และห้ามอ่านรายงานของ Builder

ข้อยกเว้นเดียวคือ dispute: Builder ส่งข้ออ้างได้ 1 บรรทัด แต่ arbiter ติดป้ายว่า "ยังไม่ยืนยัน" และ Claude ต้องตัดสินจาก log ของคำสั่งที่ arbiter รันเอง

3. ภาษากลาง: STATUS, NEXT และ ▶

ทุกคำสั่ง arbiter จบด้วยรูปแบบเดียวกันเสมอ:

4. Gate 1 และ Gate 2

🚪 Gate 1: อนุมัติ spec

เกิดก่อนเขียนงาน คุณอนุมัติ สัญญา ของงานนี้

  • Goal / Non-goals ตรงกับที่ต้องการไหม
  • AC ถ้าข้อนี้ผ่านหมด คุณยอมรับงานไหม
  • Approach วิธีทำสมเหตุสมผลไหม (KS-160 พังที่ตรงนี้)
  • scope_allow แคบพอไหม มีไฟล์แปลกไหม
  • verify คำสั่งตรวจตรงจุดไหม
  • Claude ขั้นรีวิว model ที่จะใช้ ถ้าไม่เห็นด้วยให้ทักในคำอนุมัติ

arbiter เก็บ sha256 ของ spec ไว้ ถ้า spec ถูกแก้หลังอนุมัติ ทุกขั้นถัดไปจะ BLOCKED

🚪 Gate 2: อนุมัติผลงาน

เกิดหลังเครื่องตรวจผ่านและ Claude ให้ PASS แล้ว

  • ไฟล์ที่เปลี่ยน ตรงกับที่คาดไหม
  • ผลตรวจจากเครื่อง ทุกแถว exit 0
  • ยังไม่ได้ทดสอบ ส่วนนี้สำคัญที่สุด คือสิ่งที่ไม่มีใครพิสูจน์
  • จุดที่ควรดู 1–3 จุดที่ Claude แนะนำให้คนเปิดดูเอง

arbiter ผูกการอนุมัติกับ tree ของโค้ดที่ถูกรีวิว ถ้าโค้ดเปลี่ยนหลังจากนั้นจะขึ้น STALE

นอกจากสอง Gate นี้ /spike มีจุดอนุมัติของตัวเองอีก 2 จุด คือ "อนุมัติแผน" และ "อนุมัติการ์ด" (ดู บทที่ 3)

5. หลักฐาน: evidence.json และ tree

เวลา Gemini รัน arbiter review สิ่งแรกที่เกิดคือ arbiter ถ่าย "ภาพ" ของงานตอนนั้นเป็น git tree hash (ไม่รวม .arbiter/ และเอกสารนอกการ์ด) แล้วรันการตรวจตามลำดับ:

  1. scope ไฟล์ที่เปลี่ยนต้องอยู่ใน scope_allow ทั้งหมด และต้องมีไฟล์เปลี่ยนอย่างน้อย 1 ไฟล์
  2. verify รันคำสั่งตรวจจาก config.json (เทสต์ชุดหลัก) และจาก spec ทุกคำสั่งต้อง exit 0
  3. tree-stable ถ่ายภาพซ้ำ ต้องตรงกับก่อนรัน verify (กันคำสั่งตรวจที่แอบแก้ไฟล์)
  4. Claude รีวิว เฉพาะเมื่อข้อ 1–3 ผ่าน ถ้าเครื่องตรวจไม่ผ่าน จะไม่เสียเงินเรียก Claude เลย

ผลทั้งหมดถูกเขียนลง evidence.json พร้อม tree hash ตอน arbiter commit arbiter ถ่ายภาพอีกครั้ง ถ้าไม่ตรงกับที่รีวิว จะไม่ commit

6. scope_allow และ docs_allow

scope_allow (อยู่ใน spec)

รายการ path/glob ที่การ์ดนี้แก้ได้ เขียนโดย Claude ตอนร่าง spec คุณอนุมัติที่ Gate 1 ไฟล์นอกนี้ทำให้ gate ไม่ผ่าน และ git hook ไม่ให้ commit

docs_allow (อยู่ใน config)

glob ของเอกสารที่ commit เองได้โดยไม่ต้องมีการ์ด เช่น kong-workspace/**, *.md ถ้าเอกสารเหล่านี้เปลี่ยนระหว่างทำการ์ด จะไม่ถูกนับเป็นงานของการ์ด และไม่ทำให้ STALE

กฎที่เพิ่มใน v0.3.2 ถ้าไฟล์ตรงกับทั้งสองอย่าง scope_allow ชนะ เช่นการ์ด KS-160 ที่ผลงานคือ OpenAPI spec ใน kong-workspace/notes/ ไฟล์นั้นเป็นงานของการ์ด ต้องผ่านรีวิว ส่วน AGENTS.md / CLAUDE.md / GEMINI.md ไม่นับเป็นเอกสารเสมอ

8. Claude ใช้ model อะไร

ขั้นmodel
ร่าง spec · ตอบคำถาม · spikeOpus · High เสมอ เว้นแต่คุณสั่งเองตอนเริ่มการ์ด เช่น "/feature KS-12 ใช้ sonnet medium"
รีวิว · disputeแจ้งในหน้า Gate 1 ว่าจะใช้อะไรและมาจากไหน: ที่คุณสั่ง → ที่การ์ดจาก spike แนะนำ → Opus · High ถ้าไม่ทักในคำอนุมัติ ใช้ตามนั้น ทักได้ เช่น "อนุมัติ Gate 1 ใช้ opus high"

เหตุผล: งานที่แพงที่สุดใน KS-160 เกิดจาก spec ที่ผิดตั้งแต่ต้น จึงไม่ประหยัดที่ขั้น spec ส่วนรีวิวที่ใช้ sonnet ใน KS-160 ราคาครึ่งเดียว ($0.56 เทียบ $1.11) model ของทุกครั้งที่เรียกอยู่ใน sessions.jsonl: model คือคำที่สั่ง ส่วน model_used คือรุ่นจริงที่ CLI รายงาน (v0.3.5) เช่น สั่ง fable ได้ claude-fable-5-2

ชื่อที่สั่งเองได้: haiku · sonnet · opus · fable (v0.3.4) เช่น "/feature KS-12 ใช้ fable" หรือ "อนุมัติ Gate 1 ใช้ fable high" fable ต้องสั่งเองเท่านั้น ไม่เป็นค่าตั้งต้น และการ์ดจาก spike แนะนำไม่ได้ เพราะยังเป็นสิทธิ์ทดลอง ชื่อเหล่านี้เป็น alias ที่ claude CLI แปลเป็นรุ่นล่าสุดเอง (ทดสอบ 10 พ.ย. 2026 กับ CLI 2.1.322: fable = claude-fable-5-2) ถ้าต้องการตรึงรุ่น เช่น Fable 5.1 ให้พิมพ์ชื่อรุ่นเต็มแทน alias ได้ (v0.3.5) เช่น "/feature KS-12 ใช้ claude-fable-5-1" หรือ "อนุมัติ Gate 1 ใช้ claude-fable-5-1 high" arbiter ไม่ตรวจว่ารุ่นมีจริง ถ้าพิมพ์ผิดจะได้ ERROR ตอนเรียก Claude ครั้งแรกของขั้นนั้น (เหตุผลอยู่ใน last-claude-output.txt) ถ้าจะตรึงทั้งโปรเจกต์ ใส่ชื่อเต็มใน config.json หรือตั้ง env ARBITER_MODEL

9. ภาษา

spec, คำถาม, หน้า Gate 2 และผลรีวิวจะใช้ภาษาเดียวกับข้อความล่าสุดที่คุณพิมพ์ในการ์ดนั้น ถ้ายังไม่ได้พิมพ์อะไร ใช้ภาษาไทย (ค่า language ใน config)

ลองตอบ

Gemini อยากให้ Claude ดูไฟล์ mockup ที่เพิ่งได้มา ควรทำอย่างไร ส่งเป็นตัวชี้ ใน spike ใช้ spike answer ... --file <path> ใน /feature ให้คุณบอกผ่าน answer (เช่น "ดู mockup ที่ path นี้ประกอบ") ห้าม Gemini สรุปเนื้อหา mockup แล้วส่งเป็นข้อความเอง
Gemini แก้ไฟล์งานหลัง Claude ให้ PASS แล้ว จะเกิดอะไรตอน commit tree ไม่ตรงกับที่รีวิว arbiter ตอบ STALE พร้อมรายชื่อไฟล์ และจะไม่ commit ต้อง review ใหม่
ทำไม arbiter ไม่เรียก Claude ถ้า verify ไม่ผ่าน เพราะงานที่เครื่องบอกว่าพังแล้วไม่จำเป็นต้องให้ AI อ่าน ประหยัดเงินและเวลา และทำให้ Claude ได้รีวิวเฉพาะงานที่ผ่านเกณฑ์ขั้นต่ำแล้ว
