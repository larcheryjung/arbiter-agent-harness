Arbiter

ใช้ AeroHarness ที่ทำงานเร็วเหมือนเดิม คือ Gemini เรียก Claude เองอัตโนมัติ แต่ย้ายการตัดสินว่างานผ่านหรือไม่ จาก “AI เล่าเอง” ไปเป็น “script ตัดสินจากหลักฐาน” และคุณยังกดอนุมัติแค่ 2 จุดเท่าเดิม

ทำไมต้องมีตัวใหม่

harness ตัวที่ 5 ในรอบ 3 เดือน ตัวนี้จึงสร้างจากบทเรียนของตัวก่อนๆ ไม่ได้เริ่มจากศูนย์

ตัวก่อนหน้ารูปแบบใช้คุมงานจริงบทเรียน
DUETbash CLI + กฎยาว0 งานกฎยาวกว่างานที่มันคุม
Aether Forgeforge.py + git hookไม่มีโปรเจกต์อื่นใช้ต้องพิมพ์คำสั่งเพิ่มทุกขั้น จึงไม่มีใครใช้
AeroHarnessกฎ + template + invoke-claude.ps114+ การ์ดเร็วเพราะ Gemini เรียก Claude เอง แต่ผ่านหรือไม่ผ่านมาจากที่ AI เล่า
TriumvirateNode CLIเฉพาะ testing-groundแยกบทบาทออกจาก driver ถูกทาง แต่ไม่มี gate ที่เครื่องตัดสิน

จุดอ่อนของ AeroHarness ที่ตัวใหม่แก้

ผลรันเทสต์ใน Handoff คือข้อความที่ Builder เขียนเอง เช่น “Exit code 0, มั่นใจ 100%” Gate 2 จึงเป็นการอนุมัติตามที่ AI เล่า
Gemini เขียน prompt ให้ Claude เองว่าต้องตรวจอะไร คนถูกตรวจเป็นคนกำหนดขอบเขตการตรวจ
ใช้ --dangerously-skip-permissions ซึ่งปิดชั้นบังคับชั้นเดียวที่ Claude Code มี
ไม่มีอะไรเช็ก scope_allow จริง และ 10 ขั้นเท่ากันทุกการ์ดไม่ว่างานเล็กหรือใหญ่

หลักแกน 7 ข้อ

ถ้าจำได้แค่หน้านี้ก็พอ

  1. เครื่องเป็นคนตัดสิน ไม่ใช่ AI เล่าผ่านหรือไม่ผ่านมาจาก evidence.json ที่ script สร้าง และผูกกับ hash ของโค้ดชุดที่ถูกทดสอบจริง
  2. คนกดแค่ Gate 1 และ Gate 2ระหว่างสอง gate ทำงานอัตโนมัติทั้งหมด ไม่มีการสลับ panel หรือส่งงานต่อด้วยมือ
  3. คนถูกตรวจห้ามเป็นคนเขียนโจทย์ให้คนตรวจGemini ส่งแค่ตัวชี้ (KS-xx) แล้ว Claude อ่านการ์ด, spec และโค้ดจากต้นทางเอง
  4. พื้นกันพังเป็นโค้ด ไม่ใช่ promptgit hook และ gate script บังคับได้ทั้ง Gemini และ Claude และไม่กิน context เลย
  5. harness ตัวเดียว แยกท่าตามประเภทงานโหลดเฉพาะท่าที่ใช้ ฝั่ง Gemini อ่านแค่ workflow 14 บรรทัด
  6. ส่งต่องานผ่านไฟล์ และ reset context ทุกการ์ดทุกอย่างที่สำคัญอยู่ในโฟลเดอร์การ์ด ส่วน session ของ Claude เป็นแค่ตัวช่วยให้เร็วขึ้น
  7. บทเรียนต้องย้อนกลับมาแก้ harnessสะดุดเมื่อไรให้จด 1 บรรทัด ถ้าเจอซ้ำค่อยเพิ่มตัวตรวจ ส่วนกฎที่ไม่เคยจับอะไรได้ให้ลบทิ้ง

ใครทำอะไร

ใครทำห้ามทำ
คุณก้องตอบคำถาม, อนุมัติ Gate 1 และ Gate 2, ตัดสินเรื่องที่ถูกส่งขึ้นมา—
Gemini (Antigravity)คุมงาน, เขียนโค้ด, เรียกคำสั่ง arbiter แล้วทำตามบรรทัด NEXT:เขียน prompt ให้ Claude, ตัดสินเองว่างานผ่าน, แก้ไฟล์ใน .arbiter/, commit เอง
Claude (claude -p)ร่าง spec และคำถาม, review โค้ดเทียบกับ specแก้ไฟล์ใดๆ (มีแค่ Read, Grep, Glob และ Jira อ่านอย่างเดียว)
scriptสร้าง prompt, รัน gate, อ่านผลตัดสิน, นับรอบ, สร้างหน้า Gate 2, commit—

ลำดับงาน /feature

สถานะที่ script ส่งกลับมาแสดงเป็นป้าย STATUS ซึ่ง Gemini อ่านแล้วทำตาม NEXT:

  1. คุณก้อง “ทำ KS-xx”
  2. Gemini arbiter spec KS-xx
    Claude อ่านการ์ดจาก Jira, intent.md และโค้ด แล้วส่ง spec กลับมาพร้อมคำถาม 0–5 ข้อ ทุกข้อมีค่าที่จะใช้ถ้าไม่ตอบ
    NEEDS_ANSWERS แสดงคำถามตามตัวอักษร คุณตอบ แล้ว arbiter answer KS-xx "<คำตอบเดิม>" Claude resume session เดิมแล้วแก้ spec
    READY_FOR_GATE1 แสดง spec ให้คุณอ่าน
  3. 🚪 Gate 1 คุณอนุมัติ spec
    arbiter approve KS-xx "<ข้อความอนุมัติ>" บันทึก sha ของ spec ไว้ ถ้า spec ถูกแก้หลังจากนี้ ทุกขั้นถัดไปจะถูกบล็อก
  4. Gemini เขียนโค้ดเฉพาะใน scope_allow แล้ว arbiter review KS-xx
    script ตรวจ scope และรัน verify แล้วเขียน evidence.json ถ้าผ่านค่อยให้ Claude review แบบอ่านอย่างเดียว
    FAIL Gemini แก้แล้ว review ใหม่ (อัตโนมัติ)
    ESCALATE reviewer ตีกลับครบ 2 รอบ ส่งให้คุณตัดสิน
    READY_FOR_GATE2 script สร้างหน้า Gate 2 จาก evidence และผล review
  5. 🚪 Gate 2 คุณอ่านหน้า Gate 2 แล้วอนุมัติ
    arbiter commit KS-xx "<ข้อความอนุมัติ>" ตรวจซ้ำว่าโค้ดตรงกับชุดที่ review ผ่านทุกไบต์ ถ้าไม่ตรงได้ STALE
  6. COMMITTED Gemini ขยับการ์ด Jira ตามกฎ lifecycle เดิม
ปกติคุณเข้ามา 2 ครั้ง (บวกการตอบคำถามที่ Gate 1 ถ้ามี) จะเข้ามาเพิ่มเฉพาะเมื่อเกิด ESCALATE หรือ ERROR

โครง 3 ชั้น

ชั้น 1 · Floor

ใช้กับทุกงาน เป็นโค้ดทั้งหมด จึงไม่กิน context: git pre-commit, gate script และ jira-guard (มีอยู่แล้ว 3 ชั้น)

ชั้น 2 · Track

โหลดเฉพาะท่าที่ใช้ · v0 มี /feature · ภายหลังจะมี /quick, /spike และโหมด Ops · /greenfield กับ migration รอจนมีงานจริง

ชั้น 3 · Pack

ความรู้เฉพาะเรื่อง โหลดเมื่อเกี่ยวข้อง เช่น jira-ks, spring-boot, windows-ps (ยังไม่ได้ทำใน v0)

สิ่งที่เครื่องบังคับ

ทุกข้อในตารางนี้มีเทสต์ยืนยัน

จุดตรวจอะไร
review (gate)ไฟล์ที่เปลี่ยนอยู่ใน scope_allow · รัน verify ครบ (ไม่มี verify เลย = FAIL) · คำสั่ง verify ที่มาจาก spec ห้ามมี | & ; · โค้ดต้องไม่เปลี่ยนระหว่างรันเทสต์ · spec ต้องตรงกับที่อนุมัติ
Claudeเรียกด้วย --tools Read,Grep,Glob จึงไม่มี Bash, Edit หรือ Write ให้ใช้ · ตอบตามรูปแบบที่กำหนด แล้ว script เขียนไฟล์เอง
commitevidence ต้องผ่าน · spec ตรงกับ Gate 1 และตรงกับตอน review · โค้ดตรงกับ tree ที่ review · สิ่งที่ stage ใน git index ต้องตรงกับ tree นั้นด้วย (กัน assume-unchanged และ force-add)
git pre-commitcommit โค้ดได้เฉพาะผ่าน arbiter commit · ไฟล์ต้องอยู่ใน scope ของ spec ที่อนุมัติ · บล็อก private key, AWS/Atlassian/GitHub token, .env, ไฟล์ SSH key · ห้ามแก้ config · ถ้าไม่แน่ใจจะปฏิเสธไว้ก่อน

ไฟล์ของการ์ด

.arbiter/tasks/KS-xx/ แยกจาก kong-workspace/ เดิม และ commit ไปพร้อมโค้ดเพื่อใช้ตรวจย้อนหลัง

ไฟล์เขียนโดยคืออะไร
intent.mdคนสิ่งที่คุณบอกหรือตัดสินใจไว้ (ไม่บังคับ)
spec.mdscript จากคำตอบของ ClaudeGoal, Non-goals, AC, Approach และบล็อก scope_allow / verify
questions.md / answers.mdscriptคำถามที่ยังค้าง / คำตอบของคุณตามตัวอักษรเดิม
approvals.jsonscriptGate 1 (sha ของ spec) และ Gate 2 (tree)
evidence.jsonscripttree hash, ไฟล์ที่เปลี่ยน, ผลแต่ละ check และ exit code
review.md / gate2.mdscript จากคำตอบของ Claudefindings ทุกรอบ / หน้าสรุปสำหรับ Gate 2
sessions.jsonlscriptsession_id ของ Claude แต่ละครั้ง (ใช้ claude --resume เปิดดูได้) และค่าใช้จ่าย

ขั้น 0 ที่ทดสอบบนเครื่องนี้

  • claude -p + allowlist ไม่ค้าง ถูกปฏิเสธภายใน 12 วินาที
  • -p --resume จำบทสนทนาเดิมได้
  • Gemini ส่งคำตอบของคุณต่อตรงทุกตัวอักษร (เทียบกับ transcript แล้ว)
  • PowerShell -Command เปลี่ยน exit code ที่ไม่ใช่ 0 ให้เป็น 1 หมด จึงสื่อสารด้วยบรรทัด STATUS: แทน

ข้อจำกัดที่รู้แล้ว

Arbiter ออกแบบมากัน agent ที่ทำพลาดหรือมักง่าย ยังกัน agent ที่ตั้งใจโกงได้ไม่ครบ
  • ไฟล์ใน .arbiter/ (approvals, evidence, state) agent แก้ได้ · commit ตรวจ spec, scope และ tree ซ้ำเอง แต่ยังเชื่อผล verify/review ใน evidence
  • agent รัน approve แทนคนได้ ตอนนี้ตรวจย้อนหลังได้จาก transcript ของ Antigravity
  • git commit --no-verify ข้าม hook ได้ ต้องใช้ CI ตรวจ trailer Arbiter-Tree จึงจะปิดได้
  • v0 มีแค่ /feature และยังไม่ได้ลองผ่าน Gemini ครบวงจรบนโปรเจกต์จริง

แนวทางรอบถัดไป: เก็บไฟล์หลักฐานตัวจริงใน .git/arbiter/ · ให้ approve ต้องยืนยันด้วยรหัสที่แสดงให้คนเห็นเท่านั้น · ตรวจ transcript อัตโนมัติ
