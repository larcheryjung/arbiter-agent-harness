/feature ทีละขั้น

ตามการ์ดหนึ่งใบตั้งแต่พิมพ์ /feature KS-xx จนการ์ดขึ้น Done ในหน้านี้ใช้ KS-160 (OpenAPI spec ของ Policy Status API) เป็นตัวอย่าง คุณพิมพ์จริงแค่ 3–4 ครั้ง ที่เหลือ Gemini กับ arbiter คุยกันเอง

ก่อนเริ่ม
  • ใช้กับการ์ดที่ ขอบเขตชัดแล้ว ถ้ายังไม่รู้ว่าต้องทำอะไรบ้าง ให้เริ่มที่ /spike ก่อน
  • เปิดแชท Gemini ใหม่ทุกครั้งที่อัปเดต arbiter เพื่อให้โหลด workflow ฉบับล่าสุด
  • ทำการ์ดทีละใบ arbiter จำการ์ดที่กำลังทำไว้ในไฟล์ .arbiter/ACTIVE

ภาพรวม: ใครทำอะไร ตามลำดับ

#คุณGeminiarbiterClaude
1พิมพ์ /feature KS-160รัน arbiter spec KS-160ตั้งการ์ดเป็น ACTIVE · ดึงการ์ดขึ้นบอร์ด Jira · สร้าง prompt จาก templateอ่านการ์ดจาก Jira + แผนของ spike (ถ้ามี) + โค้ด แล้วร่าง spec และคำถาม
2ตอบคำถาม (ข้อที่ไม่ตอบใช้ค่า default)แสดงคำถามตามตัวอักษร · ส่งคำตอบด้วย answerตรวจว่า Claude อ่านการ์ด Jira สำเร็จจริง · บันทึกคำตอบลง answers.mdsession เดิม (resume) ปรับ spec ตามคำตอบ
3อ่าน spec แล้วพิมพ์ อนุมัติ Gate 1รัน approve ด้วยข้อความของคุณเก็บ sha256 ของ spec + model ที่ใช้รีวิว
4เขียนงานเฉพาะไฟล์ใน scope_allow แล้วรัน reviewscope → verify → tree-stable → evidence.json
5ถ้า FAIL: แก้แล้ว review ใหม่ (หรือ dispute)นับรอบ · ครบ 2 รอบตีกลับ หรือ 6 รอบ gate → ESCALATEอ่าน spec + diff + evidence แล้วให้ PASS / FAIL / SPEC_ISSUE
6อ่านหน้า Gate 2 แล้วพิมพ์ อนุมัติ Gate 2รัน commit ด้วยข้อความของคุณตรวจซ้ำทุกอย่าง แล้ว commit พร้อม trailer
7ขยับการ์ดบน Jira: Story → UAT / QA, Task → Done

ทีละขั้นแบบละเอียด

  1. เริ่มการ์ด: /feature KS-160

    Gemini รัน arbiter spec KS-160 ถ้าการ์ดมี spec อยู่แล้วจะรัน status แทน แล้วทำต่อจากขั้นที่ค้าง arbiter จะ:

    • ดึงการ์ดออกจาก Backlog ขึ้นบอร์ด 5335 (การ์ดที่อยู่ใน Backlog แล้วปิด จะหายจากบอร์ด) และแจ้งผลในข้อความ
    • ถ้าคุณสั่ง model เอง เช่น "/feature KS-160 ใช้ sonnet medium" จะเก็บไว้ใน model.json และใช้ทุกขั้นของการ์ดนี้
    • เรียก Claude ให้อ่านการ์ดเอง ถ้าการ์ดมาจาก spike Claude จะอ่าน solution.md และการ์ดใน cards.json ประกอบด้วย
    กันการเดาถ้า Claude เรียก jira_get_issue ของการ์ดนั้นไม่สำเร็จ (เช่น Jira MCP ยังไม่พร้อม) arbiter จะไม่รับ spec และตอบ ERROR แทนการปล่อยให้ Claude เดา
  2. ตอบคำถาม: NEEDS_ANSWERS

    Claude ถามได้ 0–5 ข้อ เฉพาะเรื่องที่หาจากโค้ดไม่ได้ (business rule, ขอบเขต, การตัดสินใจที่ย้อนยาก) ทุกข้อมีตัวเลือกและ [default: …]

    • ตอบเฉพาะข้อที่ไม่เห็นด้วยกับ default ก็ได้ ข้อที่ไม่ตอบใช้ default
    • ถามกลับหรือแย้งได้ ทุกข้อความไปถึง Claude ตามตัวอักษร
    • คำตอบถูกเก็บใน answers.md และ Claude ต้องทำตาม
  3. อ่าน spec: READY_FOR_GATE1

    spec ยาวไม่เกินประมาณ 40 บรรทัด มี Goal, Non-goals, AC (Given/When/Then), Approach, Assumptions, Risks และปิดท้ายด้วยบล็อกที่เครื่องอ่าน:

    ```arbiter
scope_allow:
  - kong-workspace/notes/policy-status-api.openapi.yaml
  - kong-workspace/payloads/*.json
verify:
  - npx --yes @redocly/cli@1 lint --extends=recommended-strict kong-workspace/notes/policy-status-api.openapi.yaml
```

    ท้ายหน้ามีบรรทัด Claude ขั้นรีวิว: … (ที่มา) ใช้ checklist ใน บทที่ 1 แล้วเลือก:

    • อนุมัติ Gate 1 ถ้าจะเปลี่ยน model รีวิว ให้ต่อท้ายได้ เช่น อนุมัติ Gate 1 ใช้ opus high
    • หรือพิมพ์สิ่งที่อยากให้แก้ Gemini จะส่งด้วย answer แล้ว Claude แก้ spec
  4. Gemini เขียนงาน: APPROVED_GATE1

    arbiter แสดงรายการ scope_allow อีกครั้ง Gemini แก้ได้เฉพาะไฟล์เหล่านั้น ถ้าจำเป็นต้องแก้นอก scope ต้องหยุดถามคุณ ระหว่างนี้คุณไม่ต้องทำอะไร

  5. เครื่องตรวจ + Claude รีวิว: arbiter review

    ลำดับการตรวจอยู่ใน บทที่ 1 ข้อ 5 ผลที่เป็นไปได้:

    ผลหมายถึงเกิดอะไรต่อ
    FAIL (gate)scope / verify / tree-stable ไม่ผ่านGemini แก้เอง ไม่เรียก Claude
    FAIL (review)Claude เจอ BLOCKER หรือ MAJORGemini แก้ตาม findings หรือ dispute ถ้า finding ขัดกับความจริงของเครื่องมือ
    SPEC_ISSUEปัญหาอยู่ที่ specรอคุณตัดสิน (ดูบทที่ 4)
    ESCALATEตีกลับครบ 2 รอบ หรือ gate ครบ 6 รอบรอคุณ: ทำต่อ / แก้ spec / พักการ์ด
    BLOCKEDไม่มีไฟล์ที่เปลี่ยนตาม scopeGemini หยุด ห้ามรันซ้ำเอง
    READY_FOR_GATE2ผ่านทั้งเครื่องและ Claudeรอคุณอนุมัติ

    ตั้งแต่รอบที่ 2 Claude ตรวจเฉพาะข้อเดิมว่าแก้แล้วหรือยัง และมีอะไรพังเพิ่มหรือไม่ ห้ามเปิดประเด็นใหม่ ยกเว้น BLOCKER และต้องยึดคำตัดสินของคุณใน decisions.md

  6. Gate 2: READY_FOR_GATE2

    หน้านี้ arbiter สร้างจากหลักฐาน ไม่ใช่ Gemini เขียน มีไฟล์ที่เปลี่ยน, ตารางผลตรวจจากเครื่อง, ผลรีวิว, สิ่งที่ยังไม่ได้ทดสอบ และจุดที่ควรเปิดดูเอง

    • พิมพ์ อนุมัติ Gate 2 เพื่อ commit
    • หรือพิมพ์สิ่งที่ต้องแก้ Gemini จะแก้แล้ว review ใหม่
  7. commit: COMMITTED

    arbiter commit ไม่เชื่อไฟล์ JSON เฉยๆ แต่ตรวจซ้ำเอง:

    • evidence ผ่านทั้ง gate และรีวิว
    • spec ยังตรงกับที่อนุมัติ Gate 1
    • โค้ดไม่เปลี่ยนจากที่รีวิว ถ้าเปลี่ยนจะขึ้น STALE พร้อมรายชื่อไฟล์
    • ไม่มีไฟล์นอก scope
    • สิ่งที่ stage อยู่ตรงกับที่รีวิวทุกไบต์

    จากนั้น commit โดยมี trailer Arbiter-Card, Arbiter-Tree, Arbiter-Gate2 ส่วนเอกสารนอกการ์ดที่เปลี่ยนระหว่างทางจะไม่ถูกรวมใน commit นี้ และถูกแจ้งไว้ให้ commit แยก

  8. ขยับการ์ดบน Jira

    Story → UAT / QA (รอ BA ทดสอบ) · Task → Done · การ์ด LOCAL ไม่แตะ Jira

แก้ spec ระหว่างทาง

ถ้าเขียนงานไปแล้วเพิ่งรู้ว่า spec ต้องเปลี่ยน (ต้องการเพิ่ม AC, Approach ใช้ไม่ได้) ให้บอก Gemini เช่น แก้ spec: ให้ examples เป็น inline Gemini จะส่งด้วย answer ซึ่ง:

  • ยกเลิก Gate 1 เดิมทันที
  • Claude แก้ spec แล้วคุณต้องอนุมัติ Gate 1 ใหม่
  • งบรอบตีกลับและรอบ gate นับใหม่ เพราะถือเป็นสัญญาฉบับใหม่
  • งานที่เขียนไปแล้วยังอยู่ ไม่ต้องเริ่มใหม่

งานที่ไม่มีการ์ด Jira: LOCAL-n

พิมพ์ /feature เพิ่ม endpoint ตรวจสถานะคิว (เล่าโจทย์แทนรหัสการ์ด) arbiter ตั้งรหัส LOCAL-1, LOCAL-2, … ให้ และเก็บคำพูดของคุณไว้ใน intent.md ตามตัวอักษร ขั้นตอนอื่นเหมือนการ์ด KS ทุกอย่าง ต่างกันแค่:

  • Claude ไม่มีเครื่องมือ Jira เลย อ่านโจทย์จาก intent.md
  • ไม่ดึงการ์ดขึ้นบอร์ด และหลัง commit ห้ามแตะ Jira

เคล็ดลับ

  • คำถามที่ช่วยได้มากที่สุดตอน Gate 1: "ถ้าตอน Gate 2 คุณจะตีงานนี้กลับ น่าจะเป็นเพราะอะไร" คำตอบกลายเป็น AC ได้ทันที (Claude จะถามเองถ้าการ์ดไม่มี AC)
  • อ่าน "ยังไม่ได้ทดสอบ" ให้ดีที่สุด ตอน Gate 2 นั่นคือสิ่งที่ไม่มีใครพิสูจน์ ไม่ใช่ส่วนที่พิสูจน์แล้ว
  • อย่าให้ Gemini commit เอง ถ้าเห็น Gemini รัน git commit หรือ git checkout ให้หยุดมันทันที
  • หลังจบการ์ด เปิด Claude Code แล้วพิมพ์ retro KS-160 ให้อ่าน transcript ของ Gemini กับโฟลเดอร์การ์ด แล้วจดบทเรียนลง LESSONS.md

ลองตอบ

Gemini ตอบว่า "เทสต์ผ่านหมดแล้ว พร้อม commit" แต่ยังไม่เห็นหน้า Gate 2 ควรทำอย่างไร อย่าเชื่อ ผลผ่านมาจาก arbiter review เท่านั้น บอกให้ Gemini รัน arbiter review KS-xx และรอหน้า READY_FOR_GATE2 ที่ arbiter สร้าง
อนุมัติ Gate 1 ไปแล้ว แต่อยากให้รีวิวใช้ Opus แทน Sonnet ที่การ์ดแนะนำ ทำได้สองทาง: พิมพ์ "แก้ spec: …" เพื่อเปิด Gate 1 ใหม่ แล้วอนุมัติพร้อมบอก model (อนุมัติ Gate 1 ใช้ opus high) หรือครั้งหน้าบอกตั้งแต่คำอนุมัติแรก
เอกสารใน kong-workspace ที่ไม่ได้อยู่ใน scope เปลี่ยนระหว่างทำการ์ด จะเกิดอะไร ไม่นับเป็นงานของการ์ด ไม่ทำให้ STALE และไม่ถูกรวมใน commit ของการ์ด หน้า COMMITTED จะบอกรายชื่อไว้ให้ commit แยก (ไม่ต้องใช้ --no-verify)
